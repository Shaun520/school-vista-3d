# Blender 三维资产接入方案（方案 B）

> 适用项目：React + React Three Fiber 网页端智慧校园 3D 平台
> 文档状态：草案，待评审
> 更新日期：2026-10-23

## 1. 背景与目标

- 现有 `docs/智慧校园3D平台_原型资料/prototype.html` 是交互与视觉的**参考原型**（原生 Three.js、单文件、程序化建模），不作为最终技术栈。
- 最终项目采用 **React + React Three Fiber**，三维资产来自 Blender 建模的篮球场、教学楼等 `.blend` 文件。
- 目标：
  - 网页端流畅运行，目标 60fps；
  - 资产可独立迭代、可分包加载；
  - “走进建筑内部”定义为**地点切换**：点击教室 → 切换到室内场景，不表现具体的行走过程。

## 2. 结论

采用**方案 B**：

> Blender 中做总装校验，导出时按模块拆分 GLB，前端按布局配置拼装。

- 不导出整套校园为单一 GLB。
- 室内空间独立成 GLB，按需加载。
- 总装 `.blend` 只用于对位和检查，不直接发布。

## 3. 方案对比

| 方案 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| A. 全合并单 GLB | 总装后导出 1 个 campus.glb | 实现简单，一次加载 | 改一栋楼需重导整包；文件大；无法分栋加载/LOD；楼层拆解、POI 绑定不灵活 |
| **B. 分模块 GLB（采用）** | Blender 总装对位；每栋建筑/场地导出独立 GLB；前端按 `layout.json` 摆放 | 迭代快、可分包、可复用、可单独替换 | 需要统一的命名与坐标约定 |
| C. 混合 | 远景保留程序化，仅导入精细室内 | 首屏最快、改动最小 | 近远景风格需过渡，最终不是全真实校园 |

选择 B 的原因：项目已确定 React + R3F，模块化加载与组件化结构天然匹配；且“进入教室”是地点切换，室内天然应独立打包、按需加载。

## 4. 资产拆分与目录建议

```text
public/assets/
├─ campus/                     # 室外，首屏按需加载
│  ├─ ground.glb               # 地面/道路/绿化（可选合并）
│  ├─ teaching-building.glb
│  ├─ office-building.glb
│  ├─ basketball-court.glb
│  └─ ...
├─ interior/                   # 室内，点击进入时加载
│  ├─ classroom-a.glb
│  └─ ...
└─ layout.json                 # 位置、朝向、POI、室内入口
```

### 4.1 布局配置示例

```json
{
  "models": [
    {
      "id": "teaching",
      "url": "/assets/campus/teaching-building.glb",
      "position": [30, 0, -66],
      "rotationY": 0,
      "poi": { "name": "教学楼", "anchor": "POI_Teaching" }
    },
    {
      "id": "basketball",
      "url": "/assets/campus/basketball-court.glb",
      "position": [-20, 0, 40],
      "rotationY": 0,
      "poi": { "name": "篮球场", "anchor": "POI_Basketball" }
    }
  ],
  "interiors": [
    {
      "id": "classroom-a",
      "url": "/assets/interior/classroom-a.glb",
      "entry": [0, 1.6, 8],
      "lookAt": [0, 1.4, 0]
    }
  ]
}
```

坐标体系与参考原型保持一致：**1 单位 = 1 米，Y 轴向上，地面 y = 0**。原型中各建筑坐标可直接作为初始布局值。

## 5. 交互设计：进入建筑 = 地点切换

1. 室外场景常驻，点击建筑/教室热点。
2. 显示加载态，`Suspense` 加载对应室内 GLB。
3. 隐藏或卸载室外场景组，相机切换到室内预设机位（`entry` + `lookAt`）。
4. 退出时反向切换，恢复室外相机状态。

实现注意：

- 同一室内资产被多个教室复用时，共享 `useGLTF` 缓存，避免重复下载。
- 若要真正释放显存，需手动 `dispose()` 几何体、材质和贴图；`useGLTF` 缓存本身不会自动释放。
- 室内外切换建议加淡入淡出遮罩，避免看到穿帮和加载闪烁。
- 不需要碰撞和行走模拟，室内只需固定机位 + 有限的环视。

## 6. 性能预算

假设目标环境：桌面 1080p、集显或入门独显、校园网 20–50Mbps、目标 60fps（单帧 16.6ms）。

| 指标 | 建议上限 | 说明 |
| --- | --- | --- |
| 首屏下载体积（含 JS） | 8–12MB，硬上限 15MB | 50Mbps 约 2–4s，20Mbps 约 5–6s |
| 校园外景总三角面（可见） | 20–35 万 | 单栋建筑 2–5 万 |
| 单个建筑 GLB | 3–8MB | 合并后每栋 ≤ 6 种材质、≤ 8 个 draw call |
| 室内单间 GLB | 5–10MB，5–10 万面 | 按需加载，不占首屏 |
| 全场景 draw call | 目标 < 150，硬上限 250 | 树木、路灯、栏杆使用 InstancedMesh |
| 材质 / shader 变体 | 每模块 ≤ 6 种，全场景 ≤ 30 种 | 材质种类直接影响编译与切换开销 |
| 贴图尺寸 | 默认 1024，重点资产 2048，禁止 4K | 优先共用图集 |
| 贴图显存合计 | < 150MB，硬上限 200MB | 一张 2K RGBA 含 mipmap 约 21MB |
| 阴影 | 仅主要建筑与地面参与 | 阴影会把投射几何再渲染一遍 |

> 以上为起步假设，需用试点资产实测后修正。

## 7. `.blend` 内容控制规范

### 7.1 核心原则

**不要用 `.blend` 的 MB 数作为主要指标。** 真正决定网页性能的是导出后的三角面、材质数、draw call、贴图尺寸和显存占用。

### 7.2 源文件约束

- 单栋建筑源文件建议 ≤ 20–30MB；超过 50MB 必须排查隐藏副本、打包贴图或未使用的高模。
- 单栋外景 ≤ 5 万三角面，单间室内 ≤ 10 万三角面。
- 不打包 4K 贴图；贴图以外部文件引用，默认 1024。
- 导出前执行 `Purge Orphans`，清除孤立数据块、未使用材质和贴图。
- 删除隐藏物体、重复物体、摄像机、灯光和临时参考物。

### 7.3 导出设置

- 格式：glTF 2.0 Binary（`.glb`）。
- 勾选 Apply Modifiers；`+Y Up`。
- 仅导出选中 Collection，不导出灯光和摄像机。
- 不导出动画，除非确有需要。
- 导出后用 `gltf-transform` 做 prune / dedup / weld / 贴图降采样，再用 Meshopt 或 Draco 压缩。

### 7.4 命名即接口

节点命名直接作为前端交互的锚点，必须统一：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `POI_` | 热点锚点，前端生成标签和点击热区 | `POI_Teaching` |
| `FLOOR_` | 楼层拆解节点 | `FLOOR_01` … `FLOOR_04` |
| `ANCHOR_` | 其他定位点（入口、机位） | `ANCHOR_Gate` |
| `LOD_` | 预留多级细节 | `LOD0_Teaching` |

## 8. 加载慢与运行卡的区别

这是两笔独立的性能成本：

| 阶段 | 主要成本 | 表现 |
| --- | --- | --- |
| 首次加载 | 下载字节数、GLB 解析、贴图解码、GPU 上传、shader 编译 | 加载界面久；进入瞬间卡一下 |
| 每帧运行 | draw call（CPU）、三角面（GPU）、阴影二次渲染、贴图显存、透明 overdraw、React 重渲染 | 帧率低、转视角掉帧、偶发卡顿 |

关键结论：

- 文件大**既可能导致首屏慢，也可能导致持续卡顿**；
- 但运行卡顿的主因通常是**物体/材质拆得太碎、阴影过多、贴图显存过高**，而不是 MB 数本身；
- 一个体积较大但合并良好的模型，可能比体积小但包含数百个独立物体的模型更流畅。

### 8.1 排查指标

在 R3F 中读取 `gl.info`（即 `renderer.info`）：

- `render.info.calls`：draw call，超过 300 通常是 CPU 瓶颈；
- `render.info.triangles`：每帧三角面；
- `memory.geometries` / `memory.textures`：资源数量与泄漏；
- `programs`：shader 变体数量，过多会导致切换场景时编译卡顿。

### 8.2 症状对照

- 持续低帧 → draw call / 三角面 / 阴影；
- 第一次看到某建筑时卡一下 → 贴图首次上传或 shader 编译；
- 偶发长卡顿 → GC、React 重渲染、显存超限；
- 仅首屏久、进入后流畅 → 纯粹的下载/解析体积问题。

## 9. React Three Fiber 接入要点

- 用 `useGLTF` 加载，`useGLTF.preload` 预加载首屏必需资产；室内资产点击时再加载。
- 用 `<Suspense>` 包裹异步模型，配合加载占位与淡入。
- 几何压缩二选一：Meshopt 或 Draco，均需在加载器上配置对应 decoder。
- 动画与每帧逻辑用 `useFrame` + `ref`，避免每帧 `setState` 触发 React 重渲染。
- 树木、路灯、栏杆等重复物件使用 `InstancedMesh`。
- 阴影只对主要建筑开启；优先考虑烘焙贴图或低分辨率阴影。
- 统一色彩管理：确认 glTF 贴图的 `colorSpace`（颜色贴图 SRGB，法线/粗糙度线性），并与现有 `ACESFilmicToneMapping` 对齐。
- 组件卸载时手动 dispose 几何体、材质和贴图，防止来回进出室内导致显存持续增长。
- 参考原型的 1920×1080 等比舞台与 HUD 布局可沿用，但应改为 React 组件化实现。

## 10. 常见坑

1. **Blender 程序化材质导不出来**：glTF 只支持 Principled BSDF + 图片贴图。噪波、渐变、层材质等节点必须烘焙，否则 GLB 中会丢失。
2. **变换未应用**：总装里看着对齐，导出后错位。所有模块导出前 Apply 变换，并统一原点。
3. **本地文件加载失败**：浏览器不能直接读取 `file://` 下的 GLB，必须通过本地或正式 HTTP 服务访问。
4. **贴图显存爆炸**：4K 贴图数量多时，即使文件不大也会在运行中卡顿甚至崩溃。
5. **shader 编译卡顿**：材质种类过多时，首次进入某区域会明显卡一下。
6. **R3F 开发环境 StrictMode**：开发模式下组件会双挂载，可能看到重复加载，生产构建不会出现。
7. **课程素材版权**：若模型来自课程资料，需确认授权范围后再用于公开部署。

## 12. 实测数据（2026-10-23）

实测环境：Blender 5.2.2 LTS，glTF 导出器 v5.2.40，几何压缩使用 Meshopt。测试产物位于 `.workbuddy/glb_test/`（已被 `.gitignore` 忽略，不属于正式资产）。

### 12.1 体积与面数

| 资产 | 源 `.blend` | 原始 GLB | Meshopt GLB | 按材质合并后 | 合并 + 减面 | 三角面（原始 → 减面后） | draw call（原始 → 合并后） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 教学楼 `teachBuilding` | 60.9MB | 16.8MB | 9.5MB | 4.4MB | 2.3MB（50%） | 244,274 → 122,136 | 4,339 → 18 |
| 教室 `My classroom285` | 17.3MB | 5.5MB | 3.2MB | 2.8MB | 2.1MB（60%） | 155,084 → 93,020 | 433 → 62 |

### 12.2 贴图实测

| 资产 | 图像数 | 嵌入 GLB 大小 | 解码后显存（RGBA） | 含 mipmap 估算 |
| --- | --- | --- | --- | --- |
| 教学楼 | 9 | 0.47MB | 12.7MB | 16.9MB |
| 操场（原始） | 28 | 14.36MB | 114.1MB | 152.2MB |
| 操场（裁剪 + 1024） | 16 | 2.83MB | ≤46MB | ≤62MB |
| 教室（原始） | 45 张 | 30.8MB | 约 2,044MB | 约 2,726MB |
| 教室（混合 1024/512） | 44 张 | 7.61MB | 约 53MB | 约 70MB |

**教室贴图已补入项目并完成分级降采样**：贴图已复制到 `model/`，共 45 张、30.8MB，包含 8192×8192、5120×5120、4096×4096 等大图；直接解码约 2,044MB（含 mipmap 约 2,726MB），不可直接入包。现在 6 张主贴图（墙面、地面、黑板、课桌、讲台）保留 1024，其余降到 512，贴图体积从 32.3MB 降至 6.25MB。

操场贴图中有 `2000×2000`、`2272×1704`、`2246×1620` 等多张大图，现已降到最大 1024 后重新嵌入，嵌入体积从 14.36MB 降至 2.83MB，解码显存约 46MB（含 mipmap 约 62MB）。

### 12.3 结构与坐标规范

| 资产 | 对象结构 | 源包围盒（Blender 单位） | 源单位换算 | 归一化后尺寸（米） | 变换问题 |
| --- | --- | --- | --- | --- | --- |
| 教学楼 | 9,059 个对象（4,337 mesh + 4,721 empty），17 种材质 | 62.6 × 58.0 × 9.4 | ×2 | 125.2 × 116.1 × 18.7 | 无未应用缩放/旋转 |
| 教室 | 419 个 mesh，53 种材质 | 54.8 × 37.4 × 16.6（移除异常灯带后） | ×0.2 | 10.96 × 7.48 × 3.32 | 168 个对象缩放未应用，96 个旋转未应用 |
| 操场（纯净版） | 106 个 mesh，合并为 12 个对象 | 376.8 × 201.8 × 8.0 | ×0.5 | 188.4 × 100.9 × 4.0 | 487 个对象缩放未应用 |

补充说明：

- **三个资产使用了三种不同的源单位**。缩放系数是分别根据楼层间距（约 1.45 单位 ≈ 2.9m）、400m 跑道尺寸（376×201 单位 ≈ 188×100m）和教室层高（16.6 单位 ≈ 3.3m）推断的，需在 Blender 中人工确认后再固化为流水线参数。
- **`teachBuilding.blend` 不是单栋教学楼，而是由 8–10 个建筑体块组成的校园建筑群**（俯视图可见多栋独立建筑）。因此“楼层拆解”不能按整栋处理，必须先确定拆解对象：整个建筑群按层展开，还是只对其中一栋主楼拆解。
- **教学楼**：4,337 个 mesh 是典型的 3ds Max 导入结构，按材质合并后 draw call 从 4,339 降到 18，是本次实测中收益最大的优化。
- **教室**：归一化后为 10.96 × 7.48 × 3.32m，符合单间教室尺度；场景内包含 `扫描` 集合（11 个对象、约 7.5 万面），已整体保留。`屋顶灯` 对象的 Array 修改器相对偏移为 -23.6，导出后会生成约 170m 的异常灯带，已在导出时移除。
- **操场**：原始包围盒 1.6km × 1.3km。裁剪半径 100，并去掉 z 中心高于 3（源单位）的周边建筑/结构，最终保留 106 个 mesh、合并为 12 个对象；归一化后 188.4 × 100.9m，仅保留草地与球场，没有跑道线和看台。
- **花草资产**：`model/花草/` 共有 131 个 FBX、合计 149.1MB，尚未逐个测量，不能按原始文件直接入包。

### 12.4 最终处理结果

| 资产 | 文件 | 体积 | 三角面 | draw call | 归一化尺寸 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| 校园建筑群 | `model/web/teachBuilding.glb` | 2.42MB | 122,136 | 78 | 125.2 × 116.1 × 18.7m | 可用；含 6 个 `FLOOR_` 节点 |
| 操场 | `model/web/playground.glb` | 4.18MB | 43,290 | 12 | 188.4 × 100.9 × 4.0m | 已选纯净版；无看台/跑道线 |
| 教室 | `model/web/classroom.glb` | 9.68MB | 92,722 | 58 | 10.96 × 7.48 × 3.32m | 可用；主贴图 1024、其余 512；已移除异常灯带 |

> 当前产物暂存于 `model/web/`；搭建 React 工程后迁移到 `public/assets/campus` 与 `public/assets/interior`。

处理参数：

- 全部使用 Meshopt 压缩，加载端需配置 `MeshoptDecoder`。
- 教学楼：×2 缩放，按 6 个楼层带分组（层高 2.9m），组内按材质合并，减面 50%。
- 操场：裁剪半径 100，去掉 z 中心高于 3（源单位）的周边结构，×0.5 缩放，仅对高面数对象减面 10%，贴图上限 1024。
- 教室：×0.2 缩放，按材质合并，减面 60%；6 张主贴图上限 1024，其余上限 512。
- 已写入交互锚点：`POI_Teaching`、`POI_Playground`、`POI_Classroom`；教学楼另有 `FLOOR_01`…`FLOOR_06` 楼层节点。

### 12.5 实测结论

1. **三个源资产使用了三种不同单位，归一化是必需步骤。** 教学楼 ×2、操场 ×0.5、教室 ×0.2；若直接按 1 单位 = 1m 导入，三者尺寸会互相矛盾。
2. **按材质合并是必需步骤，不是可选优化。** 教学楼静态合并版 draw call 从 4,339 降至 18，最终楼层分组版为 78；操场从 487 降至 12，教室从 433 降至 58。
3. **贴图降采样比几何减面更能决定文件体积。** 教室贴图 30.8MB → 6.25MB，操场 14.36MB → 2.83MB；几何减面主要影响每帧渲染成本。
4. **操场必须裁剪 + 减面 + 降采样三步。** 原始 95.8MB / 156 万面，最终纯净版 4.18MB / 4.3 万面 / 12 draw call；纯净版只剩草地 + 球场，没有跑道线和看台，可在前端补画跑道线。
5. **外景预算已达标。** 教学楼 + 操场 = 6.60MB、16.5 万面、90 个 draw call，低于“桌面为主、35 万面 / 150 draw call”的目标。
6. **室内按需加载可行。** 教室 9.68MB、9.27 万面、58 个 draw call，只在进入教室时加载并隐藏外景，不占首屏。
